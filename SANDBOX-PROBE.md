## DIAGNOSIS

Core dev tooling (git, python3, node, uv) is present and correct out of the box; only `gh` was missing, and it installed cleanly via `sudo apt-get install -y -qq gh` in under a minute despite unrelated 403s from two third-party PPAs (deadsnakes, ondrej/php) that don't block the base Ubuntu repo refresh — so tool installation is not actually a blocker, just an easily-fixed gap in the base image. The most consequential finding is C4: although this session's declared sources are both `chelsealong/spec-kit` (fork) and `github/spec-kit` (upstream), the harness materialized exactly one checkout on disk, with `origin` pointing at the *upstream*, and no fork checkout anywhere in the filesystem. Adding an upstream repo to a routine's `sources` array does not, by itself, grant a second working checkout — it appears to only grant one clone, and in this case it favored upstream over the fork the task actually needed to push to. Access is split across two independent, inconsistently-scoped layers: the git smart-HTTP proxy (`local_proxy` on `127.0.0.1:41729`) and the `gh` CLI/REST layer. The proxy layer freely allows anonymous/unauthenticated-looking clones of *any* public repo (A10's plain clone of upstream succeeded even though the API layer refuses to talk about that same repo), and it allows pushes to the fork once a remote URL is manually constructed with the fork's owner/repo path (A12's dry-run succeeded) — but it flatly refuses pushes to the upstream `origin` remote the checkout ships with (A11's 403). Meanwhile the `gh api`/`gh issue`/GraphQL layer refuses *any* call touching `github/spec-kit`, the very repo declared as an in-scope source, with "GitHub access is not enabled for this session. An org admin must connect the Claude GitHub App for this organization." — the identical message returned for a repo never mentioned anywhere in scope (`google/adk-python`), so this session cannot distinguish "not in scope" from "in scope but API access still off" from tool output alone. `gh auth status` itself claims the token is invalid, yet `gh api user` and `gh api repos/chelsealong/spec-kit` succeed with that same token — the CLI's own auth check is unreliable as a capability signal here. Net effect for an OSS-contribution agent: filing an issue/PR comment, listing issues, or running any GraphQL query against upstream is impossible even read-only, while a plain `git clone`/`git push` against the same hosts works fine when addressed correctly. The single change that would most improve this sandbox is making the `gh`/REST/GraphQL access policy match the git-proxy access policy — i.e., if `github/spec-kit` is a declared source, either enable the GitHub App for it on the API layer too (so `gh api`, `gh issue list`, and GraphQL work against it, matching what raw git already permits) or fail the git clone the same way the API calls fail, so the two layers agree about what "in sources" grants instead of one silently allowing and the other silently blocking.
